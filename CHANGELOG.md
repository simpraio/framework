# Changelog

All notable changes to this project will be documented in this file.

## [5.2.0] - 2026-10-25

### Security

- Stack traces carry no call arguments once the framework handles errors: `ErrorHandler::register()` sets `zend.exception_ignore_args`. Traces are written to the log and shown on debug pages, and arguments carry request data and credentials; `#[SensitiveParameter]` protects only the parameters someone marked, and PHP's development default leaves arguments on.
- Rate limiting counts every request, including those `auth` or `csrf` turn away. Hooks ran in folder-name order and the first `before()` to return a response ended the round, so `auth` and `csrf` ran ahead of `ratelimit`: a client could send unlimited failed CSRF posts, or unlimited requests to protected pages while signed out, without spending any budget. Extensions now declare an order with `Boot::PRIORITY` - lower first, default `0`, ties in folder-name order - and `ratelimit` takes `-100`.
- Login throttling refuses a file-counter directory another local account could control; it is checked on every login check, with or without APCu. It lives in the shared temp directory, and one created beforehand by someone else - world-writable, or a link - was used as it was, so that account could delete counters to reset login throttling or plant them to lock users out. A directory that is a link, writable by group or others, or owned by another account now stops logins with `AUTH_RATE_LIMIT_DIRECTORY_NOT_PRIVATE`; one others can only read, as older releases created it, is still used. Present since the file fallback was added.
- A change to `auth_access` or `auth_group` applies on the next request. Whether a path had a route rule at all, and the list of active groups, were cached for an hour on each host: under `default_policy = 'allow'` a page given its first rule stayed public for that hour, a path whose last rule was removed went on refusing everyone, and `User::inGroup()` went on reporting a disabled group. Both are now read on every request, and a path's rules come from one query.
- Error pages for 4xx statuses no longer fill `{FILE}`, `{LINE}` and `{TRACE}` in production. Only a 5xx emptied them; a 403, 404 or other client error filled them with the server path, line and stack trace, and the shipped `error.html` hid them only because it prints them inside `{isDebug}`. A project's own `error.html` printing them elsewhere showed them to anyone who requested a missing page.
- A template block configured in `auth_access` but not granted to the current user is hidden. `Access::pathBlocks()` answered only the blocks the user had a matching rule for, and a block nobody answers is rendered with its contents, so a block granted only to another user or group was shown to everyone. A block with a numeric name lost its answer the same way when the layout's blocks were merged, and a configured block named `IsGuest` or `IsAuthenticated` could override the real value.
- Disabling an auth group withdraws its grants and keeps its denials, so it never widens access. The guest group is found by name whatever its status, so visitors keep its id and its denials when it is disabled; they used to fall to group 0, where a global allow then opened routes denied to guests. Its users fall back to user-specific rules with `group_id = 0` and global rules.
- Profiler labels are HTML-encoded, preventing comment terminators in a label from emitting markup outside the timing report.
- A failed SMTP login no longer puts the password in the error log. The encoded username and password went through the same helpers as every other SMTP command, and with `zend.exception_ignore_args` off - the development default - a rejected `AUTH LOGIN` logged a trace beginning `command('UGE1NXdvcmQtU2V...'`, the first characters of the password in base64, and a connection that dropped while the password was sent logged it whole. Every write to the SMTP connection now takes its data through a parameter marked `#[SensitiveParameter]`, and a failed write is reported without a notice that would carry it.
- A hidden template block stays hidden however large it is. `Template::blocks()` removed blocks with a regular expression, and past about 1 MB of content PCRE gave up on the backtrack limit; the failure was swallowed and the template kept as it was, so a hidden block - an admin-only table filled from a large result set, a section `Access::pathBlocks()` hid from this user - was sent anyway. Blocks are now found by plain string search, with the same pairing as before. Present since at least 5.1.0.
- `log.redact_keys` is applied to the log file. The kernel copied the log level, rotation and retention onto the writer one field at a time and left the redaction keys out, so every key listed there was written in the clear; only a writer built by hand, as the test suite did, honoured them. The writer is now built from the whole log configuration at once. Present since at least 5.1.0; logs written before the upgrade may hold those values.
- A flattened project's `config/framework.local.php` is no longer compiled into the config bundle. The loader read every `config/*.php` as a default, and a flattened project keeps its local file in that directory, so `cache/config.php` held a plaintext copy of the database password, `crypt_key` and any extension credential set there. Which ones depended only on whether a default file sorting after `framework.local.php` happened to overwrite them. A key deleted from the local file also stayed effective, served from the bundle as a default, until the bundle was cleared. Present since at least 5.0.0; a framework checkout, whose local file sits beside `framework/` rather than in `config/`, was never affected. `framework.local.example.php` and other `framework.local.*.php` variants are excluded for the same reason.
- The HTTP client refuses a URL carrying credentials - `https://user:secret@host/` - before anything is sent, and refuses a redirect to one even with the egress guard off. A URL is logged, kept in history and forwarded, and the credentials travelled with it; the refusal itself carries only a label with no user information. URLs containing whitespace, control bytes or backslashes, or with a percent-encoded host, are refused for the same reason the egress guard refuses them: another parser may read them differently. Send credentials in an `Authorization` header.
- The `Host` guard accepts only `host[:port]`. It read the header through `parse_url('http://' . $host)`, which treats everything before an `@` as user information, so `Host: evil.example@app.example.com` was judged by `app.example.com` and let through, as was a value with a path or query after an allowed host. Those are now refused with 400.
- Rate-limit counters are keyed on the policy, not only on the address. Every budget previously shared one counter and one expiry, so the per-request application-wide check and a controller's own limit spent each other's allowance, and whichever ran first fixed the expiry for both - a 600-second endpoint budget first touched behind a 2-second global one vanished after two seconds. `Limiter::exceeded()` takes an optional `$scope` to separate policies that differ only in where they are applied; the documented independent endpoint limits now behave as described.
- `error-log` redacts every query parameter named in `log.redact_keys` from the URLs it stores, as well as those in its own `redact_keys`. `log.redact_keys` is where a project names what it treats as secret, but it applied only to log context, while `error-log` writes the request's query string to the database; a name listed there - a reset token, a signed-link signature - was stored in the clear unless it was repeated in the extension's own list. A parameter is matched both as written and as PHP reads it into `$_GET`, so `token%00x`, `token[a]`, `token%5Ba%5D` and ` token` are all redacted as `token`; only the literal spelling was before. The query is split where PHP splits it, on every character of `arg_separator.input`: with `&;` configured, `?keep=1;token=secret` gives the application a `token` and is now redacted, where only `&` was recognised before.
- An outbound request header whose name ends in a line feed is dropped. The HTTP client's name check had no end anchor, so `"X-Evil\n"` passed and reached cURL as the line `X-Evil` followed by `: value`. It matters only where header names come from input; present since at least 5.1.0.
- Integer validation refuses a value too large for the type instead of saturating. `'99999999999999999999999'` matched the digit test and cast to `PHP_INT_MAX`, so an unbounded `int()` returned nine quintillion for it. Float validation refuses non-finite results: `'1e999'` is numeric and overflows to infinity, and every comparison against `NAN` is false, so `NAN` satisfied a minimum and a maximum at once.
- `Validator::uuid()` refuses a value ending in a line feed instead of returning it. Its pattern ended in `$`, which also matches before a final newline, so `"<uuid>\n"` passed and came back unchanged as a valid UUID, newline included, to be used in queries, logs or headers. The same anchor is fixed in `int()` - which accepted `"5\n"` - in integer config values, and in `Db`'s table and column name check, which accepted `"users\n"`. Present since the validation extension was added.
- A date containing a NUL is a validation failure rather than a 500. `DateTimeImmutable::createFromFormat()` raises a `ValueError` for one instead of returning `false`, and nothing caught it.
- Reading a malformed JSON body twice fails the same way twice. `Request::json()` marked the body parsed before decoding it, so the first read threw and left the cache unset while the flag said otherwise - the second returned an uninitialised-property `Error` in place of the refusal.
- Redirect targets are resolved by RFC 3986 section 5 rather than approximated, and the specification's own example table is now a test. Twelve of its forty cases were wrong: a trailing slash was dropped, so `g/` and `.` and `..` all named a resource one level up from the right one; dot segments survived in an absolute-path reference, so `/./g` was requested literally; a repeated slash was collapsed, and `/a//b` is not `/a/b`; a fragment was read as part of the path, so `g#s/../x` followed to `/x`; and a reference with no path took the base's directory instead of its path, so `?page=2` returned from `/reports/list` requested `/reports`. Each of these follows to a different resource than the server named. Resolution lives in `extensions\http_client\Reference` with section 5.2.4's algorithm in `extensions\http_client\DotSegments`, leaving `Redirect` to decide only whether a response redirects.
- A database connection whose rollback fails is discarded instead of reused. All enclosing transaction callbacks remain aborted until they exit: catching an inner error cannot reconnect and silently autocommit subsequent writes. A backend-ended transaction is also detected before further database work. A later operation outside those callbacks may reconnect.

- A failed `COMMIT` no longer abandons an open transaction. Transaction depth remains available during commit and rollback and unwinds in the transaction wrapper's `finally`. A top-level rollback is skipped when the backend has already closed the transaction itself, preserving the original failure.

- A `GET` carrying data is sent as a `GET`, and no request carrying a body is ever retried. `CURLOPT_POSTFIELDS` makes cURL switch the method to `POST` on its own, so `HttpClient::get($url, ['data' => ...])` arrived at the server as a `POST` while every decision in the client still called it a `GET` - including the rule that retries only safe methods. An ambiguous transport failure therefore replayed what the server had seen as a write: one `get()` call produced two `POST`s against a server that dropped the first connection. The verb is now stated explicitly whenever a body is present, and the retry rule reads the request rather than the verb alone, so a body disqualifies a replay whatever the method says. `HttpClient::post()` is unchanged.

- Password rehash updates match the original credential, preventing a stale login from overwriting a concurrent reset. A lost race refuses login without changing the session. Automatic rehashing raises low bcrypt costs only; stronger bcrypt and Argon2 hashes are preserved.

- The egress guard judges an address inside the NAT64 well-known prefix `64:ff9b::/96` by the IPv4 it carries rather than by the prefix's own IANA attribute. IANA marks that prefix globally reachable, which describes the prefix and not the address in its low 32 bits, and RFC 6052's rule against putting a non-global IPv4 behind it binds whoever writes a DNS record rather than whoever reads one. An allowlisted host answering `64:ff9b::a9fe:a9fe` therefore passed the guard carrying `169.254.169.254`, and any NAT64 gateway on the path would have completed the journey to the metadata service. `64:ff9b::808:808` stays reachable because `8.8.8.8` is.
- TLS for the MySQL connection is configurable through `database.ssl` - `ca`, `cert`, `key` and `verify_server_cert`, which defaults to true. There was previously no way to encrypt database traffic at all: the framework set no SSL attributes, and `database.options` reaches the driver with string keys only while every SSL attribute is an integer constant, so a CA path put there was silently dropped and the connection stayed in the clear while the configuration said otherwise. A client certificate without its key, or the reverse, is now refused when the database configuration is first read instead of falling back to password authentication unannounced; a successful boot alone does not validate these lazy settings.
- OIDC token and Graph requests require HTTPS and refuse redirects, keeping credentials and unsigned token responses bound to the intended TLS endpoint. The HTTP client exposes `follow_redirects` per request, enabled by default.

### Added

- `tools/prune-auth-counters.php` reports expired file-backed login counters and can remove them during an acknowledged worker-stopped maintenance window. Dry-run is the default; live, locked, malformed and redirected files are preserved.
- `oidc-login`: Microsoft and Google sign-in in one optional extension, with shared state/PKCE, token transport, callback and session handling. Explicit provider selection preserves independent identities, Microsoft tenant/group policy and Google's Workspace-domain allowlist. Both require verified TLS, and both are held to one `exp`/`iat`/`nbf` rule - `exp` and `iat` are required, a fractional NumericDate is accepted as RFC 7519 allows and keeps its precision at the expiry and not-before boundaries, and a time claim that is not a JSON number is refused. Both are also held to one audience rule: `aud` must be the client ID alone, `azp` must be too when present, and the nonce must be the one this sign-in created. Each configured provider answers for both of its template blocks whether or not it is enabled, because a block nobody answers for is left standing in the rendered page. `Login::start($provider, $returnTo)` returns a successful sign-in to the page that asked for it, so a protected page's `return` survives the round trip through the provider: only a path on this site is kept, it stays on the server with that sign-in rather than travelling in `state`, each tab keeps its own, and it is checked again before it is followed. A completed sign-in lasts `session_max_age` seconds - 8 hours by default, `0` for the life of the session, with `clock_skew` tolerated on the sign-in time - because the provider is not asked again afterwards: an account disabled there, or removed from a required group, would otherwise stay signed in here indefinitely. Switching the extension's root `enabled` off switches every provider off with it, so a disabled extension needs no credentials. Its live probe, `tests/live/oidc-login.php`, reports a certificate-verification error as a failure rather than as a missing local prerequisite. See [setup and registration](docs/18-Extensions-OIDC-Login.md).
- `extensions\auth\State::sessionPayload()`, a shared session payload for already-authenticated accounts, including external sign-in and impersonation flows. It binds the session to the current stored password value, including a successful rehash, and removes the password from the payload. An empty string is appropriate only when the stored value is empty or null.
- `extensions.auth.return_param` (default `return`), the query parameter the guest gate appends to `guest_route` so a sign-in can return to the page that was asked for. The gate redirected to a bare `guest_route` and discarded the request, which left the receiving end of this - a login form reading `return` - with nothing to read: the feature existed on one side only. Only a path on this site is appended, it is URL-encoded so a target's own query string survives, a `#fragment` in `guest_route` stays after it so the parameter still reaches the login controller, and the sign-in page itself is never its own target, whether or not its path ends in a slash - the framework's own default `guest_route` is `/login/`, and a gate that refused the sign-in page would otherwise have nested the target one level deeper on every redirect. Only a request sent as `GET` or `HEAD` carries a target, because signing in sends the user back with a `GET`; an unknown method is not counted as one. Set the key to an empty string to switch it off: the target reaches access logs and browser history, which a project with sensitive query strings may not want. Other sites receive only the origin under the security extension's default `Referrer-Policy`. Someone already signed in who is refused carries nothing, because signing in again would not grant them the page.
- `core\http\Url`, the one place a URL or a path is taken apart or judged, so no caller needs its own `parse_url()`: `path()` is everything before the query or fragment and cannot fail; `isLocal()` is the rule `Response::redirect()` applies to a target, for code that must decide before it redirects; `configuredPath()` turns a configured route into a path on this site, and `extensions\auth\Config::redirectPath()` delegates to it; `parse()` returns a `core\http\AbsoluteUrl` - scheme, lower-cased host, effective port, `origin()` and a log-safe `label()` - or `null`; `host()` reads a `Host` header. The egress guard, its DNS pinning, the HTTP client's origin checks and log labels, the OIDC transport and redirect URI, the `Host` guard, the request path, the guest return target and the access-denied log all use it. `parse()` refuses outright what two URL parsers can read differently - whitespace, control bytes, backslashes, a percent-encoded host - since the code that checks a URL is not the code that connects to it, and a suite holds the egress guard and cURL to the same reading of every URL it accepts.
- `core\Session::rotate()`, what a sign-in or any privilege change does to the session: a new ID, the old one invalidated, and the CSRF token dropped so one issued before sign-in cannot be replayed after it. `auth` and `oidc-login` both use it. The token's key is `Session::CSRF_KEY`, and `extensions\csrf\Guard::SESSION_KEY` is defined from it, so an extension that rotates the session does not need the optional `csrf` extension to know where the token lives.
- `core\http\Request::rawMethod()`, the request method as the client sent it, upper-cased. `method()` is unchanged and still maps any method outside the ones the framework handles to `GET`, which CSRF protection relies on; `rawMethod()` is for code that must not take an unknown method for `GET`.

### Fixed

- Registry route language is initialized before controller dispatch, so controller calls may omit the language as documented.
- Outbound HTTP responses retain only the latest response header block, preventing `100`, `103`, and proxy connection headers from contaminating final response metadata and JSON decoding.
- Error-log text is normalized to valid UTF-8 and truncated at character boundaries within the database byte limit, preventing silent loss of long multibyte error messages. The exception class name is stored as ASCII, the column's character set: an anonymous class name carries a NUL and its file's path, which could make the insert fail.
- SMTP passwords retain leading and trailing whitespace instead of changing the configured credential.
- A URL naming an abstract controller or a non-controller class under `modules\` answers 404 instead of 500. Any class the URL named was dispatched, so `/admin/base-controller` tried to instantiate an abstract base and `/shop/cart` a helper, and each visit logged an error. Only a concrete `core\Controller` subclass is a route now; anything else falls back to the template or a 404.
- `project.allowed_hosts` set to anything but a list is a config error, `null` included. It was read as an empty list, which switches Host validation off, so `'allowed_hosts' => 'app.example.com'` in the config, or `null` in a local file overriding it, let every Host through to routing while looking configured. A missing key or `[]` still switches the check off.
- An `allowed_hosts` entry that can never match is a config error. Entries are compared with the `Host` header's host part, without the port, so `example.com:8443` - the natural way to allow a non-default port - refused every request with 400, as did `*.example.com` and a Unicode name, which browsers send in `xn--` form. The error names the entry.
- `Validator::uuid()` refuses a version outside 1-8 with `InvalidArgumentException`. The version was placed in a regular-expression character class as it stood, so `uuid('id', 12)` accepted version 1 and version 2 UUIDs, and `0` or `-1` matched characters no version has.
- An unknown `project.timezone` stops the boot with `Config: 'project.timezone' must be a timezone PHP knows`. The kernel set the timezone after registering its error handler, so the refusal became an exception that the handler then failed to log - the log writer needs the timezone too - and every request ended in a 500 that explained nothing.
- Registry, SEO and translation lookups log a warning when the database fails, as route aliases already did. Each caught every exception and rendered without the data, silently, so an outage showed up only as pages missing their content. All four now go through `core\cache\Optional::remember()`: a failure is logged once per key per request with the error class, later lookups in that request get the fallback without retrying the database, and nothing is cached, so the next request tries again. Only exceptions fall back; an `Error` - a bug such as a `TypeError` - propagates instead of rendering a page silently without its data.
- `Response::json()` throws `JsonException` for data JSON cannot carry instead of answering 200 with the body `null`. A single string that was not valid UTF-8 - one latin1 value from an old table - replaced the whole response, and the client could not tell an empty result from a failed one.
- Microsoft group memberships share one normalization rule: group IDs are lowercased and empty or duplicate entries are removed, including when restoring a session. Unknown memberships remain distinct from a known empty list.
- Configuration casting and validation share integer-range checks; configuration loading shares dotted-key lookup. Validation uses fewer internal rule objects without changing its public methods. HTTP option construction no longer goes through redundant policy and normalization helpers.
- Generic regression assertions now live in their owning suites instead of a separate battery harness. Local HTTP checks share server startup and cleanup; HTTP benchmarks report timings without treating machine-dependent latency as a test failure. The obsolete pipeline benchmark was removed.
- The access-denied log records the real path for one `parse_url()` cannot read, such as `/x:80/login`, where it logged `/`. An absolute-form request target is still logged by its path alone, so credentials in it never reach the log.
- A deprecation no longer ends the request. `error_reporting(E_ALL)` plus an error handler that raised everything in the mask meant a single `E_DEPRECATED` anywhere turned a page into a 500, so a routine PHP upgrade could take a site down rather than leave a note. Deprecations are now logged at warning level and the request continues; every other severity still stops it.
- A database failure while the route-alias map is cold no longer outlives itself. `Aliases` caught the error inside the cache callback and returned an empty map, which `Cache::remember()` then stored for the full TTL - an hour by default - so a database unreachable for one second answered "this site has no aliases" long after it recovered, and every aliased URL returned 404. The failure now propagates past the callback, so nothing is cached and the next request retries. It is also logged, where before both catches were silent.
- `Auth::login()` upgrades bcrypt hashes below PHP's default bcrypt cost after password verification, without lowering higher costs or replacing other algorithms.
- `auth\State::credentialFingerprint()` marks its parameter `#[SensitiveParameter]`, so a logged stack trace shows the algorithm rather than the start of the stored hash.
- The egress resolver restores PHP's error handler in a `finally`. A throw between installing the suppressing handler and restoring it would have left it in place for the rest of the request, disabling the handler that turns warnings into exceptions.
- Responses and outbound requests apply one header field rule, `core\http\HeaderField`: a name is an RFC 9110 token, and a value holds no CR, LF or NUL. `Response::header()` accepted any name without CR, LF, NUL or a colon, so a space or a non-ASCII character reached the wire; it now throws for them, and a name or value in `extensions.security.headers` that breaks the rule is refused as a config error naming the key. The HTTP client already required a token name but let a NUL through in a value, where cURL cut the header short at it; such a header is now dropped like one carrying CR or LF.
- The HTTP client refuses a method it does not send with `HttpClientException('HTTP client method rejected')` instead of sending a `GET`. `TRACE`, `PROPFIND` or a typo went out as a `GET` - a different request from the one asked for, which could succeed against the wrong handler. A non-string method is refused the same way. A missing, `null` or empty method means `POST` when `data` is set and `GET` when it is not; an empty string used to skip that choice and become `GET`, which with `data` would now have reached the server as a `GET` carrying a body. The accepted methods are `core\http\Request::METHODS`, now public and shared with `Request::method()`, so the two lists cannot drift.

## [5.1.0] - 2026-09-10

### Fixed

- Redirect targets containing ASCII control characters or DEL are rejected before a `Location` header is created, and auth redirect configuration rejects them during hydration. Browsers remove tabs and newlines while parsing URLs and treat backslashes as slashes, so a value such as slash-tab-backslash-host could otherwise pass the local-path guard and be interpreted as a protocol-relative external redirect.
- The `Message-ID` domain is derived from the validated from-address instead of the raw one. `messageId()` re-read `$message->fromEmail ?? $config->fromEmail` directly, bypassing the `FILTER_VALIDATE_EMAIL` check applied to the `From` header, so an address whose last `@` was followed by CRLF injected headers into the message while `From` itself fell back safely to the configured address. `Composer::build()` now resolves the address once and passes it to both.
- The SMTP envelope sender is taken from that same validated address rather than parsed back out of the rendered `From` header. The header also carries the display name, so a from-name shaped like `Support <helpdesk@other.test>` became `MAIL FROM`, misdirecting bounces and breaking alignment with the configured domain. `Envelope` carries the validated address and rejects invalid sender or recipient values before the SMTP transport serializes them. Address-shaped display names are quoted as one name instead of producing ambiguous mailbox syntax.
- Generated headers stay within the RFC 5322 limit of 998 octets per line. Subjects are encoded into bounded RFC 2047 encoded-words when needed, including long unbroken ASCII values; attachment filenames use bounded RFC 2231 continuations; recipient lists fold between addresses; and oversized display names are encoded. Long custom headers are rejected. Short ASCII subjects remain unchanged.

- The egress guard pins the connection to the addresses it validated. It resolved a host, approved what it saw, then handed the NAME to cURL, which resolved it independently — so an allowlisted host whose DNS answers differently between the two lookups was checked at one address and dialled at another. The validated addresses are now supplied as `CURLOPT_RESOLVE` on the same handle, and every redirect hop and retry is authorized and pinned in turn rather than inheriting the first hop's decision. Addresses come from a short per-process DNS cache, so a retry inside that window reuses them instead of resolving afresh - they were validated when first seen, and the pin is what makes them the ones dialled. A host that does not resolve at all is refused instead of allowed, since having no addresses to validate meant the check never ran.
- The egress guard requires an address to be globally routable, not merely outside the private and reserved ranges. Reachability is decided by a static classification of the IANA registries, matched longest-prefix-first so a specific entry overrides the block containing it - PCP anycast at `192.0.0.9/32` is reachable although `192.0.0.0/24` around it is not. IPv6 starts denied and is opened by the `2000::/3` global unicast allocation, because the special-purpose registry lists carve-outs rather than the allocation boundary: reserved space such as `4000::/3` or `fe00::/9`, and the deprecated IPv4-compatible `::/96` where `::7f00:1` is `127.0.0.1`, is not routable merely by being absent from it. PHP's filter flags apply only to addresses the table does not classify, where they can withhold but never permit: `FILTER_FLAG_GLOBAL_RANGE` is documented as following RFC 6890's global attribute but classifies from an incomplete list, and on PHP 8.4 and 8.5 accepts IPv4 and IPv6 multicast, `64:ff9b:1::/48`, `100:0:0:1::/64`, `3fff::/20` and `5f00::/16`. `64:ff9b:1:7f00:0:100::` is the RFC 6052 encoding of `127.0.0.1` under that prefix. IPv4-mapped addresses (`::ffff:0:0/96`) are refused as a range, `::ffff:169.254.169.254` and `::ffff:8.8.8.8` alike: IANA does not mark that range globally reachable, and an IPv4 destination is reachable by its own address. Shared address space (`100.64.0.0/10`), benchmarking and documentation ranges are refused now; a deployment reaching a genuine internal service on one of those — carrier-grade NAT is the usual case — must set `block_private_ips` to `false` or route the call through a globally routable endpoint. Special-purpose ranges that RFC 6890 marks as globally reachable, such as the NAT64 well-known prefix `64:ff9b::/96`, stay allowed.
- `CURLOPT_PROXY` is always sent, empty when no proxy is configured. Leaving it unset does not mean "no proxy": libcurl then falls back to `http_proxy`, `HTTPS_PROXY` or `ALL_PROXY` from the environment, and the request would be resolved and dialled by that proxy with nothing in the configuration saying so.
- A configured proxy also sends `CURLOPT_NOPROXY` empty, so no host is exempt from it. Setting a proxy does not otherwise stop `NO_PROXY`/`no_proxy` in the environment from exempting a host and connecting directly - and since a proxy may only be configured while the egress guard is not enforcing addresses, where this client pins nothing, such a connection would have neither proxy enforcement nor an address check.
- A configured `extensions.http-client.proxy` is refused at boot while the client is enabled and the egress guard is enabled with `block_private_ips`. A proxy resolves the destination itself, so the validated addresses are never the ones connected to and `CURLOPT_RESOLVE` cannot reach that lookup. Set `block_private_ips` to `false` to state that the trusted proxy owns the policy, or remove the proxy to keep enforcement in the application.
- The HTTP client refuses to send when cURL rejects any option. `curl_setopt_array()` stops at the first rejected option and applies none after it, so the URL could be set while the pinned addresses, method, headers and body were not.

### Changed

- PHP `mbstring` is now an explicit framework requirement. Mail composition throws `MAIL_MBSTRING_REQUIRED` if it is unavailable instead of reaching an undefined function.
- `Envelope::__construct()` retains its original four arguments and accepts an optional fifth `fromEmail` argument. When omitted, a valid final mailbox in the `From` header is used.
- A header value that cannot be represented is refused instead of encoded: a subject carrying invalid UTF-8, a line break, or any other control character except tab now throws `InvalidArgumentException('INVALID_MAIL_HEADER_VALUE')`. A display name keeps its own rule - free text, so a line break there is flattened to a space. Header values go on the wire as printable ASCII and tab: a message with raw UTF-8 header fields requires SMTPUTF8 (RFC 6532), which the sender must request in `MAIL FROM` once the server advertises it (RFC 6531), and this client negotiates none of that - so raw Unicode would be sent unannounced. Unicode still reaches the wire encoded, by RFC 2047 for subjects and display names and RFC 2231 for attachment filenames. A raw non-ASCII custom header is dropped, and `Envelope` refuses one (as `INVALID_ENVELOPE_HEADER`), along with control characters and malformed UTF-8, which that rule excludes by construction, since both transports write those bytes out directly and `mail()` checks none of them; a CRLF is accepted there only when it begins a folded continuation line. An application putting untrusted text in a subject should expect that failure. Tab is unaffected, being legal header whitespace. `$msg->subject()` trims spaces and tabs only, so a control character at either edge is refused like one in the middle rather than quietly removed.
- `$msg->header()` additionally ignores a name that is not a valid RFC 5322 field name, a value that is not printable ASCII and tab - a control character, a raw non-ASCII byte even in well-formed UTF-8, or malformed UTF-8 - and any header whose rendered line would exceed 998 octets. A name such as `X-A: b` or `Ünicode`, and a value holding a NUL or a vertical tab, previously produced a malformed header line rather than being rejected. Only spaces and tabs are trimmed from a name or value, and the value is judged before it is trimmed, so a control character at either edge drops the header instead of being quietly stripped and the rest delivered.
- `extensions.auth` takes `guest_route`, `denied_redirect` and `logout_redirect` as the path to redirect to when the value starts with a slash. They were always rebuilt as `/name/`, whatever was configured, so a project whose canonical URLs carry no trailing slash could not express one: a guest reaching a protected page was sent to `/login/`, which the site's own rewrite then sent to `/login`, costing a redirect on every protected page. Configuration could not avoid it, because the value was stripped of slashes before the shape was reapplied. A bare name still becomes `/name/`, so a configuration written that way is unaffected; write `/login` to get `/login`. A value that already carried a leading slash does change: `'/login'` produced `/login/` before and produces `/login` now. Both forms reach the same controller, since the router strips trailing slashes, but the redirect target differs - add the trailing slash to keep the old one. `Auth::logout($route)` applies the same rule to a route passed at the call site, where it previously always produced `/name/`. Leading slashes and backslashes collapse, so a configured value can only name a path on this site.

## [5.0.0] - 2026-08-30

### Added

- `session.cache_limiter` (default `nocache`), so the cache headers PHP stamps on any response that started a session are a stated setting rather than whatever `php.ini` happened to hold. Supported values are `nocache`, `private`, `private_no_expire`, and `''`; `public` is rejected because it would make every session-backed response eligible for storage by shared caches. Set `''` only when the application sets a safe `Cache-Control` header on every such response.
- `Session::hasCookie()`, which reports whether the request presented a non-empty session cookie without starting one. It deliberately does not claim that the identifier maps to stored session data.
- `tools/schema/migration-utc-storage.sql`, which converts the framework tables' locally stored instant columns to UTC for projects adopting the change below. Run it only in a maintenance window, after setting the previous storage timezone and verifying named-zone support when needed. A value whose conversion cannot be resolved - an unloaded named zone, or a stored date `CONVERT_TZ` cannot read - is left as it stands rather than written as `NULL`, and the script ends by reporting how many rows each table skipped. Values in a DST transition window cannot be detected that way, because `CONVERT_TZ` resolves both the repeated and the nonexistent hour to a deterministic instant; the script instead reads the zone's transition history and, before converting anything, records those rows and their original local values in a `simpra_dst_review` table, because they are indistinguishable once converted. It also records itself in a `simpra_migration` table, so a second run cannot shift the data twice.
- `tools/verify-vendored.php`, which compares a project's flattened framework copy against this checkout using each repository's Git filters.
- A shared, discovered test layout under `tests/core/`, `tests/extensions/`, and `tests/integration/`.
- `Format::escape()` takes a `trim` argument, defaulting to the trimming it already applied. Template token escaping and the error-page fallback now go through it instead of calling `htmlspecialchars()` directly, so the framework escapes output in one place. The flags and encoding stay fixed at `ENT_QUOTES | ENT_SUBSTITUTE` and UTF-8 so no caller can weaken them.

### Changed

- **Breaking:** MySQL connection sessions are pinned to `+00:00` instead of following `project.timezone`. One setting previously answered two unrelated questions - what humans read, and how instants are stored - so `DEFAULT CURRENT_TIMESTAMP(6)` columns held local wall clock. **Stop every database writer, deploy 5.0.0, convert existing instant columns with `tools/schema/migration-utc-storage.sql`, and only then resume writes.** Any other order can mix local and UTC rows. `Database::fromArray()` now takes only the raw config array instead of a second project-timezone argument, and the database DTO no longer exposes a timezone property; database storage timezone is deliberately not configurable.
- The MySQL init-command PDO option is reserved by the framework: it carries the UTC pin, and a connection built with an application value for it is refused rather than silently overwritten. Run any additional session setup explicitly after connecting. Note that `database.options` only ever reaches the connection with string keys, so a PDO attribute constant set there was already being dropped before this release; that is a separate gap and is not fixed here.
- `Auth::login()` writes `last_login_at` with `UTC_TIMESTAMP(6)`, matching the new storage contract. The v5 migration converts existing values because v4 wrote them through the project-timezone formatter.
- The error-log extension no longer stamps `created_at` from PHP. It used the display formatter while purging compared against the database clock, so the two agreed only while both were in the same zone; the column's own default now writes it.
- Error pages send `robots: noindex, nofollow`, so a crawled 500 cannot compete in search results with the page that was meant to load, and declare `color-scheme: light dark` in the markup as well as in `error.css` - the stylesheet failing to load is exactly the case this page must survive.
- The template-free fallback error page uses the configured project name and links home instead of hardcoding the Simpra wordmark, so products do not need to patch vendored core for fallback branding.
- Generic suites are discovered instead of listed, can run from either the framework checkout or a flattened project, and report unmet database prerequisites as skips instead of false passes. Benchmarks moved to `tools/bench/`, the cache helper moved to `tools/clear-cache.php`, and the former top-level battery is now `tests/integration/battery.php`.
- The deployment security probe accepts `--csrf-path`, never follows redirects, and reports an off-origin redirect for a missing route as a warning rather than mistaking it for proof that the route was safely rejected.

### Fixed

- Routes that map to neither a controller nor a template now return `404` before route-scoped extension hooks run. This prevents deny-by-default authentication from redirecting nonexistent URLs to sign-in. Because the application rate limiter is a route hook, missing routes no longer reach it; see UPGRADING for the behavior change.
- Anonymous visitors are no longer issued a session by mistake. Session start is lazy by design, but the auth extension's contributor hook runs on every rendered page and read the session — and reading one starts it — so every first-time visitor and every crawler was handed a cookie and a session file, and the page went out with `Cache-Control: no-store`, uncacheable by any shared cache. The hook now resolves a request carrying no session cookie as a guest without touching the session; logging in, flash messages and CSRF tokens still start one on demand.
- Removed the error page's dead SQL error-detail scaffolding. `isSQL` was hardwired to `false` and the `SQL_QUERY`/`SQL_BINDS` tokens to `''` from the day they were added, so the error page never printed any SQL and the block never rendered — it was never a working feature. If your own `templates/error.html` still contains the `{isSQL}...{-isSQL}` block, delete it when upgrading: `Template::blocks()` only rewrites the names it is given, so the leftover markers would otherwise render literally on the error page.

## [4.0.0] - 2026-07-26

### Added

- `401` and `403` responses are logged at `warning` with the request method, route path and `REMOTE_ADDR`. Other 4xx responses stay unlogged so a `404` sweep cannot flood the log. The query string is omitted because it may carry credentials or personal data, and the username is not recorded because the denial is logged by the core error handler, which has no notion of identity.
- `Cast::oneOf()` for configuration keys that are effectively enums: it matches case-insensitively, returns the canonical spelling, and rejects anything else at boot.

### Changed

- **Breaking:** `log.level` and `session.same_site` are now validated against their accepted values (`debug`, `info`, `warning`, `error` and `Lax`, `Strict`, `None`) instead of accepting any string, so **a deployment carrying an invalid value no longer starts** — it fails at boot with a message naming the key. Check both keys before upgrading. Values are matched case-insensitively, so existing spellings such as `lax` keep working. Both failed silently before: a misspelled `log.level` made every log call raise "Undefined array key", which the error handler promoted to a 500, while an unrecognised `same_site` was emitted verbatim and then ignored by the browser, quietly weakening the cookie without otherwise disturbing the application.
- Session revalidation also refreshes `group_id` from the database, so a group change takes effect within `revalidate_interval` instead of only at the user's next login.
- **Breaking:** `Cast::bool()` rejects a blank or whitespace-only string instead of reading it as `false`, so a boolean config key set to `''` now fails at boot rather than silently resolving to `false`. `filter_var()` maps `''` to `false` rather than to a failure, so such a value quietly disabled whatever the key controlled while `Cast::int()` and `Cast::string()` rejected the same input.
- **Breaking:** error-page internals moved into a `core\error` subsystem: `core\ErrorPage` is now `core\error\Page`, and the security-header emission extracted from `core\ErrorHandler` is now `core\error\SecurityHeaders`. The `core\ErrorHandler` facade and its behavior are unchanged; update any project code that referenced `core\ErrorPage` directly.

### Fixed

- Transaction depth is now dropped before the `COMMIT`/`ROLLBACK` statement is issued. A statement that threw previously left the connection permanently one level deep, so every later transaction in the request nested a `SAVEPOINT` into a transaction that no longer existed. The rollback attempted after a failed commit also no longer replaces the caller's exception with "there is no active transaction", so the deadlock or lost connection that actually broke the write is the one reported.
- `Cache::remember()` releases its stampede lock even when the callback throws. The lock previously survived for its full TTL, so with a one-hour entry every request for an hour lost the lock, slept, re-checked a still-empty key and computed anyway.
- The logger no longer throws on an unrecognised level, regardless of validation: an unknown message level is treated as an error so it is surfaced rather than filtered away, and an unknown threshold falls back to the default. `Log::setLevel()` is public API, so the level can still arrive unvalidated at runtime.
- The login-throttle fallback used when APCu is unavailable behaved as a sliding window: it rewrote each counter's expiry on every failed attempt, so a host that kept failing held its own block open indefinitely — locking out everyone sharing that address. It now honors the documented fixed window, matching the APCu path.

### Security

- Login throttling no longer keeps a blocking per-username counter. It let an unauthenticated attacker lock any known account out of the application by distributing failed logins across source addresses — no credential needed, and no recourse for the real user. Both counters are now anchored to the source address: a tight `(username + IP)` counter, plus a looser per-IP counter that still caps one host enumerating many accounts.
- A session is now bound to the credential it was issued for. `Auth::login()` stores a fingerprint of the stored password hash and session revalidation re-derives and compares it, so **changing or resetting a password signs out fingerprinted sessions** instead of leaving them valid until they expire. Sessions created before this release carry no fingerprint and are upgraded in place on their first revalidation, so upgrading does not log everyone out; a password change made before a legacy session is first revalidated cannot revoke that session by fingerprint because no old fingerprint exists yet.
- Error pages no longer publish an unfilled CSP nonce. They render outside the Response/Extensions pipeline, so the security extension never substitutes the `{_csp_nonce}` placeholder, and `'nonce-{_csp_nonce}'` was emitted verbatim — a fixed, source-visible value that looked like a working control. The whole `'nonce-...'` expression is dropped instead, leaving error pages under the same policy without the nonce, which is stricter.

## [3.0.0] - 2026-07-12

### Changed

- **Breaking:** the default Content-Security-Policy `style-src` no longer includes `'unsafe-inline'`. Inline `<style>` blocks and `style="…"` attributes are now blocked by the browser unless the CSS is served as an external stylesheet. If your application relies on inline styles, move them into a stylesheet under `public/` (recommended) or add `'unsafe-inline'` back to `style-src` in `config/security.php`.
- The framework error page now loads its styles from `public/assets/css/error.css` instead of an inline `<style>` block, so the default error page still renders correctly under the tightened CSP.

## [2.0.0] - 2026-06-05

### Added

- `Db` equality conditions (`count`, `value`, `values`, `update`, `delete`) now accept `null` values (rendered as `IS NULL`) and array values (rendered as `IN (...)`, with an empty array matching nothing).
- Per-process DNS resolution cache for outbound egress host checks, avoiding repeated blocking lookups within a worker.

### Changed

- **Breaking:** renamed the `httpclient` and `errorlog` extensions to the hyphenated directories `http-client` and `error-log` (namespaces `extensions\http_client` and `extensions\error_log`); the class autoloader now maps underscored namespace segments to hyphenated directory names. Upgrading: rename `config/httpclient.php` → `config/http-client.php` and `config/errorlog.php` → `config/error-log.php`, and the `extensions.httpclient` / `extensions.errorlog` config keys to `extensions.http-client` / `extensions.error-log` — a leftover old key is silently ignored, so your settings under it won't apply — then clear the bundle cache on deploy.
- **Breaking:** configuration layers now deep-merge maps but replace lists wholesale instead of overlaying them by index, so a local or environment layer can shrink or clear a default list rather than only overwriting elements.
- **Breaking:** `Db::update()` now returns the number of rows matched by the condition rather than only the rows whose values changed; do not infer "did anything change?" from its return value.
- UUIDv7 identifiers are now strictly monotonic within a millisecond, improving database index locality for sequential inserts.
- Default configuration files now load in a deterministic, sorted order, making the merged result reproducible across filesystems.
- `Cache::set()` now reports success when APCu is unavailable, so cache writes degrade gracefully to the per-request memory tier instead of failing.

### Fixed

- The HTTP client no longer accumulates unreleased cURL handles across retries.
- `Cast::int` now rejects out-of-range integer strings instead of silently overflowing to a clamped value.
- Invalid UTF-8 in a log context value no longer discards the entire context payload.
- MySQL connections use the `Pdo\Mysql` class constants when available, avoiding the `PDO::MYSQL_ATTR_*` constants deprecated in PHP 8.5.

### Security

- The outbound HTTP proxy is now operator-config only (`extensions.http-client.proxy`); a request-supplied `proxy` option can no longer route traffic around the egress/SSRF allowlist.
- Request JSON bodies are decoded with a bounded nesting depth (`project.max_json_depth`, default 64), mitigating a cheap denial-of-service vector.
- SMTP STARTTLS connections now pin the expected peer name, closing a hostname-verification gap on the TLS upgrade.
- Disabling TLS verification for the HTTP client (`verify_tls = false`) is refused at startup unless explicitly acknowledged via `tls_insecure_acknowledged`.
- Database and SMTP configuration objects now redact their secrets from `var_dump()` and `json_encode()` output (gated by `log.redact_secrets`, on by default).
- The class autoloader validates every namespace/class segment, preventing path traversal through crafted class names reaching the loader.
- Operators can now tighten security allowlists (e.g. the egress allowlist, `log.redact_keys`) from a local config layer, since list values are replaced rather than index-merged.
- HTTP client redirects are followed manually with the egress/SSRF allowlist re-checked on every hop, so an allowlisted host can no longer redirect the request to an internal target.
- HTTP client redirects strip `Authorization`, `Proxy-Authorization`, and `Cookie` headers and drop the cookie jar when the target changes origin, preventing credential leakage across hosts.
